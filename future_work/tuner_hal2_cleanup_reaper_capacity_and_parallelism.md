# Tuner HAL cleanup reaperの予約容量と物理同時実行数の再評価

## 位置付け

本項目は、PR #227 の上位PRで扱う**未確定の設計判断**である。既存の製品契約・実装済み動作の正本ではなく、現在の仕様は `TUNER_HAL_DESIGN_JA.md` の0-S-1と `tuner_hal2/control/src/lib.rs` を参照する。対応を決める前に数値や実装方式を既定値として先行固定しない。

- 基点：PR #116 から存在する `WorkerRuntimeReaperQueue` の `max_lanes = capacity` と `ensure_lanes(pending_group_count())`。
- 関連：PR #227 のcleanup回復監督、満杯時の非同期受付、世代付き義務管理。
- 元の指摘：[PR #227の予約容量・176 laneレビュー](https://github.com/kazuki0824/tv/pull/227#discussion_r4504379799)。
- 現行値：公開Demux 8、Filter 58、DVR 16、`cleanup_reaper_capacity = 176`。これらは現行構成の事実であり、176件の物理cleanupを並列実行する必要性の証明ではない。

## 判断が必要な問い

1. `ObjectCloseTxn` が保有する世代付きの未完cleanup義務と別に、reaperが独立した**予約件数上限**を所有する必要があるか。予約グループは物理実行権限・送信待ち・解放待ちのどれを代表し、どの時点で解放可能か。
2. 予約キューが有界である必要性と、その上限を公開オブジェクトの瞬間最大数に比例させる必要性は別問題である。世代を跨ぐ旧予約を含め、各上限の意味と枯渇時の安全動作を定義できるか。
3. 物理cleanupの**同時実行数**は別の有界なworker poolで管理すべきか。worker数を予約グループ数に追随させる方式と、少数の固定／独立上限poolではどちらが必要な進行条件を満たすか。
4. backend I/Oが無応答でも世代fenceを維持しつつ、他ownerの回収をどう進めるか。worker数を増やすことを、回復不能の認定やプロセス再起動の代替とみなしていないか。
5. runnerが`Closed`を確定してから予約グループを返却するまでの窓を、二重返却・親子委譲・ID再利用競合を増やさず縮められるか。別groupが実行中の場合の満杯は、窓の短縮だけでは解消しないことも評価する。

## 最小構成の比較候補（未採用）

| 候補 | 簡素化の可能性 | 失ってはならない条件 |
|---|---|---|
| 現行方式を維持 | 追加実装をしない | 最大176 laneの資源負荷とblocking時の進行保証を説明する |
| 予約容量とworker上限を独立化 | 一時的な予約滞留でthread数が増え続けない | 全workerが無応答の場合でも、正規の世代fence／期限監督が止まらない |
| 既存義務から直接受付する簡素なbounded queue | 別の予約台帳・全件横断照会を減らせる可能性 | 親子にまたがる一意の物理cleanup権限、未完義務、報告受理、グループ解放を破綻させない |

上記は選択肢の列挙であり、worker数を8、16、82、176のいずれかへ変更する設計決定ではない。特に単一worker化は、blocking backendにより別ownerの回収が停止する可能性があるため、無条件には採用しない。

## 判断のための検証と受入条件

- 実際のbackend別cleanup I/Oが同期・割込み可能・期限付き・無応答のどれかを確認し、通常時と故障注入時の同時実行数、p95/p99回収時間、live/旧世代予約数の上限・分布を記録する。
- 複数の同時実行上限で、最大lane数、ピークthread数、スタック予約量、RSS・CPU・スケジューリング負荷、再利用可能になるまでの遅延を比較する。
- 全worker占有、特定ownerの永久停止、別ownerの正常完了、容量1と製品容量176の予約解放遅延を再現し、局所隔離・期限監督・共有状態停止の境界を検証する。
- `ObjectCloseTxn` の世代付き義務は未完のまま消さない。親子ownerの二重物理cleanup、報告受理前の`Closed`確定、再利用されたIDへの旧世代完了適用を発生させない。
- 飽和だけを根拠に無関係なセッションを`ServiceCritical`へ昇格させず、実際のfence不能や監督機構の破損と区別する。
- Android Soong/atest、HAL再起動・Binder再接続、CTS/VTSの検証は、設計比較を採用して実装を変更する場合の独立した受入条件とする。現時点で実行済みとは扱わない。

## 完了条件と変更先

比較の結果、現状維持とする場合も、独立上限へ変更する場合も、その根拠を**現行設計正本の該当節**へ集約する。実装変更が必要なら、この上位PR内で最小限の差分と回帰試験を追加する。現行契約の変更をこのfuture_work項目だけで確定してはならない。設計判断・必要な実装・試験が所定の文書とコードに反映された後、本項目を削除する。

PR #227の終端常駐是正、局所隔離と非同期受付の変更範囲を、この未決定課題の調査だけを理由に拡張しない。
