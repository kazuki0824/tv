# Tuner HAL2 共通部品の物理化設計

## 本書の責務

本書は、`tuner_hal2` の共通化対象について、論理契約を Rust 実装へ一意に対応付けるための **A/B/C 分類、正規の Rust 物理形、命名規則、並行実行境界、重複実装禁止規則**の変更内容を整理する。

本書は新しい規範正本を追加しない。公開 AIDL の意味、状態、戻り値、能力値、資源寿命、段階、確定点、巻戻し・後始末、失敗時の意味は `../tuner_hal/DESIGN_JA.md` を正とする。実装の所有者・アンカー、許可された入口、禁止された迂回は `DESIGN_JA.md` を正とする。本書に記載する物理化規則は、それらの正本を実装へ一意に接続し、重複実装・迂回実装を監査できる形へ整理するためのものである。

本書でいう「28件」は、次を合わせた **28個の共通化対象**を指す。

1. `../tuner_hal/DESIGN_JA.md` 0-S-3B の正規共通契約20件。
2. 0-S-3B 外だが、現行設計が共通の処理責務として一意化している8件。

共通化対象の件数は論理状態・責務の単位で決め、Rust 型・ファイル・モジュールの数を理由に分割しない。判定の木で A/B/C を確定した後に、必要な Rust 物理形を決める。

`DemuxFilterDvrTxn<'a>`、`FrontendTxn<'a>`、`GenerationBoundaryTxn` のような現在の実装アンカー名は、それ自体を追加の論理契約として数えない。

## 1. 判定の木

A/B/C の分類と、分類後に必要となる論理上の追加要件は、次の木だけで判定する。Rust の命名・ファイルやモジュールの配置、スレッドへの配置、共有参照方式、`Send` / `Sync` はこの木では判定せず、物理実行方式を選んだ後に2章の実装規則を適用する。

```text
共通化対象
│
├─ 呼出しを越えて状態の正本を持つか
│   │
│   ├─ はい → A
│   │          └─ 一意な状態所有者 + 一意な変更入口
│   │
│   │          ├─ 競合する操作要求が複数の実行主体から並行到達し得るか
│   │          │   ├─ はい → 正規入口で順序を一意に確定できることを要求
│   │          │   │          └─ 具体的なロック、単一所有実行主体、命令キュー等は物理形で選ぶ
│   │          │   └─ いいえ → 並行要求の線形化要件を追加しない
│   │          │
│   │          └─ 古い操作や競合する操作を識別しなければ整合性を保てないか
│   │              ├─ はい → 必要な世代番号・権限札などを追加
│   │              └─ いいえ → 追加しない
│   │
│   └─ いいえ
│       │
│       ├─ 複数段階の手順そのものを一意化する必要があるか
│       │   │
│       │   ├─ はい → B
│       │   │          └─ 一意な手順所有者 + 明示された正規入口
│       │   │
│       │   │          ├─ 通常の関数制御だけで進行順序を保持できるか
│       │   │          │   ├─ はい → 追加の状態機械を持たない
│       │   │          │   └─ いいえ → 呼出しごとの進行状態 + 明示的な列挙型の状態機械
│       │   │          │                  └─ 段階ごとに保持できる値が異なるなら、値を列挙子に持たせる
│       │   │          │
│       │   │          └─ 手順が複数の実行主体にまたがるか
│       │   │              ├─ はい → 型付き要求・結果・一回性権限で接続し、B自身の共有永続状態を作らない
│       │   │              │          └─ 共有永続状態が必要ならAとの責務分離を再判定
│       │   │              └─ いいえ → 一つの実行主体が呼出し単位の進行状態を所有
│       │   │
│       │   └─ いいえ → C
│       │              └─ 一意な状態を持たない分類・変換関数
│       │
│       └─ C には分類だけを理由とする状態機械・世代番号・権限札・排他制御を追加しない
```

この判定木は `Send` / `Sync` を出力しない。必要な並行性・順序・所有境界を先に確定し、その後に選んだRust物理形で実際にスレッド境界を越える型、または共有参照される型だけにauto trait要件を付ける。

## 2. 判定後に適用する共通の実装・接続規則

本メモ内では、判定の木で得た分類と追加機構に対して適用する共通の実装・接続規則を本章へ集約する。後続章は、対象ごとの割当、検査方法、完了条件だけを記載し、本章と競合する別の共通規則を追加しない。

### 2.1 A の実装規則

```rust
struct ObjectCloseTxn { /* 非公開の正規状態 */ }
struct SourceBoundaryTxn { /* 非公開の正規状態 */ }
struct StreamBoundaryTxn { /* 非公開の正規状態 */ }
```

- 正規論理契約名と正規状態所有 Rust 型名を一致させる。
- 状態フィールドと変更用基本操作は、所有者外から直接変更できない可視性にする。
- 正規の変更入口は当該状態所有型に置く。
- 同じ正本状態を別の型・モジュールが影の状態として保持してはならない。
- 状態所有型と補助処理を同じファイルに置くことや、補助処理を別ファイルへ分割すること自体は制約しない。

### 2.2 B の標準形

次は許容する標準形の一例であり、専用モジュールと `execute()` という組合せだけを唯一の物理形とはしない。

```rust
mod queue_cleanup_txn {
    pub(crate) fn execute(...) -> Result<..., ...> {
        ...
    }

    fn validate(...) -> Result<..., ...> { ... }
    fn prepare(...) -> Result<..., ...> { ... }
    fn commit(...) -> Result<..., ...> { ... }
    fn rollback(...) -> Result<..., ...> { ... }
}
```

### 2.3 B の進行状態形

次も許容する標準形の一例である。

```rust
pub(crate) struct QueueCleanupTxn {
    state: State,
}

enum State {
    Prepared { /* この段階だけの値 */ },
    Running { /* この段階だけの値 */ },
    Finalizing { /* この段階だけの値 */ },
    Done,
}

impl QueueCleanupTxn {
    pub(crate) fn execute(...) -> Result<..., ...> { ... }
}
```

B 共通の規則:

- 論理契約ごとに正規手順所有者を一意にする。
- 正規手順所有者または正規入口の Rust 識別子・経路には、正規論理契約名そのもの、またはその機械的な `snake_case` 形を直接現す。これを当該契約の**正規名称標識**とする。
- 専用モジュールの作成は必須ではない。同じファイル・モジュールに複数の論理契約を配置してよいが、それぞれの正規名称標識と手順所有者・入口を一意に追跡できなければならない。
- 正規入口は契約上必要な一つ、または有限で明示された操作集合とする。関数名を一律に `execute` へ固定しない。複数の入口が必要な場合も同じ手順所有者に属し、正規名称標識を経由して追跡できなければならない。
- `validate` / `prepare` / `commit` / `rollback` 等の段階別補助処理と、存在する場合の可変な実行状態は、正規の呼出元から見える公開面に出さず、呼出元が同じ手順を再構成できる公開面を作らない。
- 呼出し単位の文脈型を置く場合、その型名を正規論理契約名と一致させること自体は必須ではない。ただし、それを別の正規手順所有者と誤認できる公開入口にしない。
- 呼出元は正規入口を使用し、同じ手順を手書きで再実装してはならない。
- B の複合手順を API 別、ワーカー別、下位実装別に複製しない。

### 2.4 C の実装規則

```rust
mod worker_failure_classifier {
    pub(crate) fn classify(...) -> WorkerFailureCategory {
        ...
    }
}
```

- 正規分類器の所有者または正規関数の Rust 識別子・経路には、正規論理契約名そのもの、またはその機械的な `snake_case` 形を直接現し、正規名称標識とする。
- 専用モジュールの作成は必須ではない。
- 公開する正規関数は、その意味を表す一つの関数とする。
- 正規関数は、呼出元が未分類の失敗値を再分類する必要のない型付き結果を返す。
- 呼出元が生の `errno`、文字列、下位実装の詳細等から同じ分類を再実装してはならない。

### 2.5 `Send` / `Sync` の実装規則

`Send` / `Sync` はA/B/C分類または論理上の並行要求から直接導出しない。論理設計が固定するのは、どの状態・手順を誰が所有し、どの要求が競合し得て、どの順序・世代柵・一回性を守る必要があるかまでとする。

Rust物理形を選んだ後、次の実際の利用境界にだけauto trait要件を付ける。

- 値そのものの所有権をスレッド間または別の実行主体へ移す型には `Send` を要求する。
- 同じ値への共有参照を複数スレッドから利用する型には `Sync` を要求する。
- 正本所有型へ並行して操作要求が到達し得るという理由だけで、その正本所有型自身へ `Send` / `Sync` を要求しない。
- 単一所有実行主体、アクター、命令キュー、メールボックス、型付き指示・結果等で契約上の並行性を満たす物理形を許容する。この場合、正本所有型自身がスレッド間を移動または共有参照されないなら、その型自身への `Send` / `Sync` は不要である。
- 従属するハンドル、権限、準備済み値についても、正本所有型のtraitから機械的に導出せず、実際に越える境界ごとに判定する。

`Send` / `Sync` はRustのauto traitなので、要求が生じた実際の型については原則としてフィールド構成からコンパイラに導出させる。`unsafe impl Send` / `unsafe impl Sync` は、ワーカーや実行器のtrait境界を満たすためだけには追加しない。必要な場合は、フィールドごとのスレッド安全性と別名参照の安全性を証明できる下位ラッパーに限定する。

物理形の決定後に正のtrait要件が付いた型は、コンパイル時検査で確認する。

```rust
fn assert_send<T: Send>() {}
fn assert_sync<T: Sync>() {}
```

どの具体型に上記検査を適用するかは、論理契約名ではなく、その物理形で実際に所有権移動または共有参照が発生する境界から決める。安定版Rustで非 `Send` / 非 `Sync` を構造的に要求する場合は、`negative impl` を前提にせず、フィールド構成と `compile-fail` 相当の検査、またはリポジトリで採用する静的検査で意図を確認する。

### 2.6 共有・並行処理の接続規則

- A に排他制御が必要な場合、その同期手段の所有者とロック順序を A の設計に含める。A の意味を曖昧にする外側からの無条件な `Arc<Mutex<A>>` 包装を標準形にしない。
- B が並行処理を開始する場合、B 自身の可変な進行状態は一つの調停者が所有し、各並行処理は型付きの結果を返し、調停者が結果を集約して進行状態を進める。
- B が共有調停を必要とする場合、関連する A が設計上提供する正規の同期・世代・権限機構を迂回しない。
- C の入出力が別の実行主体のスレッド境界を越える場合、必要な `Send` / `Sync` 要件はその境界の契約に置き、C 自身へ不要な並行制御責務を持たせない。

### 2.7 命名と一意性

全 A/B/C に次を適用する。

1. 正規論理契約名から、正規の状態所有者・手順所有者・分類器所有者と正規入口を直接追跡できなければならない。
2. A は正規論理契約名と正規状態所有型名を一致させる。B/C は2.3/2.4の正規名称標識により、正規所有者・入口の経路上へ論理契約名を直接現す。
3. 本来当該共通部品を使用すべき本番コードの呼出元が、正規名称標識を経由しない別名の所有者・入口を呼んでいる場合、それ自体を重複実装・迂回実装・旧実装残存の監査上の異常信号として扱い、同一責務の再実装かどうかを確認する。
4. 補助処理、接続用処理、Binder 生成物の保管主体、下位の状態所有者は、それぞれの責務に応じた別名を持ってよい。ただし、正規の手順・状態・分類の代替入口として公開しない。
5. 一つの論理契約を一つのファイルまたは一つのモジュールに閉じ込めることは要求しない。責務境界を保つ限り、ファイル移動、モジュール分割、補助処理の分離を許容する。
6. 物理ファイルの経路とディレクトリ配置は論理契約識別子にしない。
7. 同じ責務を実装する第二の正規所有者を設けない。契約上複数の正規入口が必要な場合は、一つの所有者に属する有限な入口集合として明示し、すべて正規名称標識から追跡可能にする。
8. 名称変更が必要なら、論理契約名、実装アンカー、正規名称標識、呼出元、対応する検査を同じ変更で更新する。旧名を同一責務の互換入口として恒久的に残さない。
9. 現在の実装名を残すためだけに正規論理契約名を曲げない。

現行 `StreamBoundaryTxn -> GenerationBoundaryTxn` は、正規状態所有者自体が論理契約名と異なる個別不整合である。`StreamBoundaryTxn` が正規論理契約である以上、正規の Rust 状態所有型も `StreamBoundaryTxn` とする。

## 5. 検査規則

28件すべてについて、正規部品が存在するだけでは設計適合とみなさない。

### 5.1 正規登録

各共通化対象について、次が一意に追跡できなければならない。

- 正規論理契約名
- A/B/C
- 正規の状態所有者・手順所有者・分類器所有者
- 正規名称標識
- 正規入口または明示された正規入口集合
- `DESIGN_JA.md` が正本として保持する実装アンカー
- 許可された呼出元
- 禁止された迂回
- 所有する状態または手順
- 判定の木が追加を指示した場合の追加要件

同じ責務に第二の正規所有者を登録してはならない。

### 5.2 共通実装規則の確認

各対象について、2章の該当規則を満たすことを確認する。ここでは2章の実装・接続規則を再定義しない。

### 5.3 設計・実装一致確認

各共通化対象について少なくとも次を確認する。

1. 正規の状態所有者・手順所有者・分類器所有者と正規名称標識が正確に一つ追跡できる。
2. 全ての意図された呼出元が、正規名称標識を経由する正規入口を使用する。
3. 本来正規所有者を使うべき呼出元が別名の所有者・入口を呼んでいる場合は監査異常として抽出し、重複実装・迂回実装・旧実装残存の有無を確認する。
4. 禁止された呼出元が下位の基本操作へ直接到達しない。
5. Aの所有状態を別モジュール・型が影の状態として保持または直接変更しない。
6. Bの段階順序が呼出元へ再展開されておらず、同じ手順をAPI別・ワーカー別・下位実装別に複製していない。
7. Cの分類規則を呼出元が再実装していない。
8. 判定の木で得た分類・追加要件、および2章の共通実装・接続規則に一致する。
9. `unsafe impl Send` / `unsafe impl Sync` が存在する場合、2.5の条件を満たす。
10. 走査コールバックの生成・配送経路は `FrontendTuneScanTxn` が確定した現走査世代の柵を必ず通り、旧世代のメッセージ配送または追加メッセージ専用の第二の走査状態機械を持たない。
11. 通常payload FMQを持つFilterの水位分類は `FilterWatermarkClassifier` を通り、呼出元が同じ閾値計算・比較境界を再実装せず、独立した水位状態機械・キュー・ワーカー・タイマーを持たない。
12. DVRの開始直後評価、状態変化時評価、周期評価は `DvrWatermarkClassifier` を通り、同じ `DvrSettingsSnapshot` と同一FMQ観測値を入力として使用し、Playback/Recordの分類式を評価契機ごとに複製しない。
13. `PacketPipeline`へのすべての通常パケット入力は型付き`TsInputOrigin`を伴い、物理経路から入力元を推測・再構成せず、通常パケット処理の第二の正規状態所有者または正規手順所有者を設けない。
14. `LnbControlTxn`はBとして呼出しを越える状態・世代・失敗状態・操作ロックを持たず、永続状態と物理LNB・レール単位のI/O直列化は`LnbRegistry`だけが所有する。公開制御、固定給電、安全状態復帰、DiSEqCのbackend I/Oが同じ物理I/O権限を通り、I/O権限待ち中にregistry状態ロックを保持しない。

### 5.4 未使用コード・静的検査

正規実装へ移行した後、同じ責務の代替正規経路として残る旧ラッパー、旧取引用ファサード、旧入口は残さない。

一方、正規所有者内部からだけ使用する補助処理、接続用処理、オブジェクト種別固有処理、Binder生成物や状態の所有者は、責務が独立しており第二の正規経路を作らない限り、別名・別ファイルのまま残してよい。

`dead_code` 等による静的検出を使う場合も、生きている重複実装は検出できないため、前項の全呼出元・全変更経路の検査を省略してはならない。
